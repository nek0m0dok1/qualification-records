# 資格管理アプリ：Codexによる実装と35日間の開発計画

## 1. 目的と完成条件

資格と取得年月、受験履歴を簡単に記録・確認できるアプリを完成させる。実装はCodexエージェントが担当し、利用者が仕様確認・操作確認・審査資料の判断を行う。

審査提出物は**プロダクトとスライドのみ**。スライドは利用者が自作し、Codexは作成しない。技術書や別冊の報告書も作成せず、プロジェクト内のdocsは実装の判断を揃えるために更新する。

- 編集範囲は `C:\Users\MimiC\qualification-records` 配下のみ。
- 対応環境はPCのChrome・Edge、AndroidのChrome。
- 資格100件・受験履歴300件で動作を検証する。この件数を登録上限にはしない。
- 必須機能は、認証、一覧・詳細、登録・訂正・削除、検索・絞り込み、JSONバックアップ・復元。
- オフライン閲覧・検索は補助機能。事前取得した記録だけを対象とする。
- 自由タグは必須機能が完成し、予備日を残せる場合だけ追加する。

## 2. 技術構成と画面

**Vue 3・TypeScript・Vite・Vue Router・Firebase Authentication・Cloud Firestore・Firebase Hosting・vite-plugin-pwa**を採用する。Firestoreの永続キャッシュを使用し、IndexedDBを直接管理する保存処理は実装しない。

画面、入力検証・記録の連動ルール、Firestoreへの保存処理を分ける。連動や日付の処理は画面に埋め込まず、単体で検証できるTypeScriptの関数にする。テストにはVitest、主要操作にはPlaywright、アクセス制御にはFirebase Emulatorを使用する。

- 初期画面はあなたの資格一覧。受験履歴一覧と切り替えられる。
- あなたの資格はカード表示とし、タップすると詳細ポップアップを開く。任意のメモを保存できる。
- 検索・絞り込み・並び順は画面ごとに独立して保持する。再読み込み時は初期状態に戻す。
- 登録は既存文書のウィザードを使用する。途中で閉じる・移動する場合は警告を表示し、そのダイアログを閉じた後に入力と進捗を破棄する。
- ポップアップはキーボード操作、フォーカス移動、スマートフォンの表示に対応する。
- URLは `/qualifications`、`/exam-attempts`、`/settings`、認証関連ページとする。通常のパス形式を使い、HostingとService Workerで直接アクセス・再読み込みに対応する。

固定タグは「語学」「IT」「ビジネス・金融」「法律・行政」「工業・技術」「医療・福祉」「教育・保育」「生活・文化」「その他」の9種類。表示名とは別の固定IDで管理し、名称変更や新規選択の停止に対応できる共通定義にする。

## 3. データ・認証・保存の仕様

### 認証とオフライン

- アカウントは必須。初回登録時に確認メールを送り、確認リンクによる本人確認後に記録機能を利用できる。
- 以後はメールアドレスとパスワードでログインする。確認メールの再送とパスワード再設定を用意する。
- Security Rulesでも本人のUIDとメール確認済み状態を検証する。
- 永続キャッシュは「この端末に記録を保存する」の選択時だけ有効にする。未選択・利用不能の場合は再起動後のオフライン閲覧を保証しない。
- ログイン、アプリへの復帰、再接続、保存後に再取得する。手動更新も用意し、重複した取得要求はまとめる。
- オフラインやサーバー取得失敗時は保存済みデータと最終取得日時を表示し、変更操作を無効にする。初回未取得は空の一覧と区別する。
- 通常の変更はトランザクションで保存し、関連データをまとめて確定する。通信断時の変更を後で自動送信する機能は設けない。Firestoreのトランザクションはオフラインでは失敗する。[公式仕様](https://firebase.google.com/docs/firestore/manage-data/transactions)
- ログアウトでは表示状態を消し、Firestoreを終了してキャッシュを削除する。他タブが削除を妨げる場合は、閉じるよう案内し、削除済みと表示しない。
- Service Workerは画面のファイルだけを保存し、認証・DB通信を追加キャッシュしない。新版は更新案内から切り替え、入力中に強制再読み込みしない。

### 記録と検索

既存の資格情報・取得情報・受験履歴の3種類を維持する。取得情報は同じ資格に1件とし、取得年月、最新更新年月、根拠となる受験履歴ID、直前の更新情報1つを保持する。履歴なしの取得・更新も許可する。

- 結果訂正と、それに伴う保有情報の変更は一組にする。同意しなければ全体を取り消す。
- 最初の取得の根拠を取り消す場合、取得・更新情報をまとめて削除する。資格情報と他の履歴は残す。
- 最新更新の取り消しは、直前の情報へ1回だけ戻す。控えがなければ最新更新情報を削除する。
- 受験履歴の削除は必ず確認する。取得・更新の根拠なら、削除・巻き戻しへの影響も表示してまとめて実行する。
- 直前更新の控えが参照する履歴を訂正・削除する場合は、巻き戻し候補から外れることも確認し、無効な関連付けを残さない。
- 資格全体の削除では、関連する取得情報と受験履歴も削除する。
- 保有情報単独の削除は提供しない。開発用の未対応処理に「保有情報のみの削除は未実装です」を設定し、docsに将来の再検討事項として残す。

名前検索は表記揺れを吸収しない部分一致。複数タグはAND条件で絞り込み、未選択なら全件を対象とする。名前検索と絞り込みもANDで組み合わせる。

日付は検証済みの文字列として扱う。取得・更新は `YYYY-MM`、受験日は `YYYY-MM` または `YYYY-MM-DD`。更新年月が取得年月より前なら拒否し、受験日は独立させる。並び順は初期降順で昇順へ切り替え可能。日不明の履歴は両方向とも同月の末尾、同日ならIDで順序を安定させる。

### JSON全置換

バックアップは、形式バージョン・書き出し日時・固定タグ定義・3種類の記録・連動と巻き戻しに必要な情報を含む。認証情報は含めない。文書IDを論理IDとして使い、JSONにはIDを明示する。

Firestoreの保存領域を利用者ごとのデータセットに分け、有効なデータセットIDを管理する。

1. サーバーから全記録を取得できた場合だけJSONを書き出す。
2. 復元前に形式、バージョン、日付、ID重複、参照関係をすべて検証する。
3. 件数と全置換の警告を表示する。事前バックアップは任意。
4. 新しいデータセットへ分割して保存し、保存内容を確認する。
5. 準備完了後、有効データセットIDをトランザクションで切り替える。
6. 切り替え前の失敗では既存領域を維持する。切り替え結果が不明な場合は、利用者UID・切替前の保存領域と更新番号・切替先IDを端末に保持し、画面移動や再読み込み後も再実行と通常変更を止める。利用者の明示操作でサーバー状態を確認し、対象への切替成功・未切替・他の切替を区別する。未切替の確認では切替先を終結状態にし、同じトランザクションで有効データセットIDを維持したまま利用者更新番号を進める。これによりcleanupが終結領域を削除しても古い更新番号の遅延切替を拒否する。確認できない間、または端末の保留状態を読み書きできない間は保留を維持して通常変更と復元を停止する。同一UIDの複数タブではWeb Locksで通常変更・復元予約・保留解除を直列化し、保留のstorageイベントを同期する。
7. 旧領域や失敗した準備領域は削除する。中断した削除は次のオンライン利用時に再開し、恒久的な追加バックアップにはしない。

復元中および切替結果の確認待ちでは通常変更を止める。他端末の変更も検出できるようデータセットの更新番号を検証し、準備中に既存記録が変わった場合は切り替えずに再確認を求める。保留状態はUIDごとに分離し、別アカウントへ引き継がない。

## 4. 35日間のスケジュール

日数は着手日を1日目として数える。Codexの実装速度だけに依存せず、利用者の確認時間、実機検証、資料修正を確保する。

| 日程 | 作業 | 区切りの完成条件 |
|---|---|---|
| 1〜2日目 | 決定事項をdocsへ反映。開発環境・テスト・Firebase設定・CIを整備。スライド用の画面・説明素材を整理する | 型チェック・ビルドが通り、必須仕様と未実装項目が明文化される |
| 3〜5日目 | 認証、本人のアクセス制御、基本保存を実装。JSON切り替えとキャッシュ削除を先に試作 | メール確認と利用者間の分離が動き、難しい保存処理の成立を確認できる |
| 6〜12日目 | カード一覧、詳細、検索・絞り込み、登録ウィザード | 主要な登録分岐を通して、保存した資格を確認できる。利用者が一度操作レビューする |
| 13〜18日目 | 訂正・削除・更新取り消し・JSON書き出しと全置換を完成 | 確認ダイアログと連動が動き、復元失敗で既存データが維持される |
| 19〜25日目 | オフライン表示・再取得・キャッシュ・新版更新、公開手順と審査用データを整備 | 本番相当の環境で一連の操作ができる。25日目で必須機能を凍結する |
| 26〜28日目 | PC・Androidで総合検証、性能確認、重大な不具合修正 | 主要シナリオとアクセス制御の検証を完了する |
| 29〜32日目 | 利用者がスライドを作成。Codexは依頼に応じて製品の画面・仕様・デモ情報を提供し、プロダクトとの整合を確認する | 審査用アカウントで主要シナリオを実演でき、スライドと製品の説明が一致する |
| 33〜35日目 | 予備日。提出前確認、障害対応、最終修正 | プロダクト、提出URL、認証情報の案内が揃う。新機能は追加しない |

利用者が作成するスライドには「利用者の困りごと→解決方法→主要画面→工夫→成果と今後」の構成を推奨する。紹介用画像・数値・機能の説明は実装と一致するよう確認し、未実装機能を実装済みとして扱わない。

## 5. 検証と運用上の前提

- 登録分岐、戻る操作、警告後の破棄、結果訂正の同意・取消、履歴削除、更新の1回巻き戻しを検証する。
- タグAND条件、名前の部分一致、日付の実在性、日不明の並び順を単体テストで確認する。
- 他人の領域、未確認メール、不正な項目・参照への保存をSecurity Rulesのテストで拒否する。
- JSONの往復、不正ファイル、準備中の通信断、同時変更、切り替え結果不明、後片付けの中断を検証する。
- オフライン再起動・検索、通信断時の保存禁止、ログアウト後のキャッシュ削除、キャッシュ利用不能、新版の更新案内を実ブラウザーで確認する。
- GitHub Actionsでは型チェック・単体テスト・Rulesテスト・ビルドを公開前に実行する。Hostingは検証成功後だけ公開し、Rulesの適用は別の手順として管理する。
- Sparkプランを前提に、Firestore Standard版を計画上の既定とする。実装開始時に実際のプロジェクト・版・無料枠を確認し、無断で課金へ変更しない。
- 審査用アカウントはメール確認済みの通常権限で用意し、架空の資格・履歴を登録する。認証情報はコードや公開スライドへ記載せず、提出先の指定方法で渡す。

## 初回実装の進行状況

初回実装では、Vue 3・TypeScript・Vite、Firebase Authentication・Cloud Firestore、画面、登録・訂正・削除、検索・絞り込み、JSON全置換、オフライン閲覧用のPWAシェルを実装した。型チェック・ドメイン単体テスト7件・本番ビルドは成功した。本番ビルドにはFirestoreのチャンクサイズ警告がある。Firebase Emulator上のSecurity Rules検証はJavaが環境にないため未実施。Firebase実プロジェクトを接続した認証・保存とブラウザー実機のオフライン動作も、接続設定後に検証が必要である。

ドメイン取得は保留し、Firebase Hostingの標準URLを使う。スライドは利用者が作成し、Codexは作成しない。初回実装の完了報告では、未実施の審査・コードレビューを実施済みと扱わない。

復元の切替結果が不明な場合の保留状態、UIDごとの永続化、サーバー確認による成功・未切替・競合判定を実装した。未切替の解除では切替先を終結させて利用者更新番号を進め、cleanup後も遅延した準備・切替を拒否する。端末状態の破損・利用不能時は変更を停止し、同一UIDの複数タブの開始・終了と通常変更をロックで直列化する。復元確認ダイアログの前後とロック取得後にUID・head・選択ファイル・利用可否を再検証する。対応する単体テスト、型チェック・lintは成功し、確認待ち中の画面更新を検証するE2E回帰テストを追加したが未実行である。
